Recurring tasks
Say "every Tuesday" once and the right task shows up forever — with taskpilot staying a program that only works when you run it. No daemon, ever.

01The shape: lazy, on-run generation

Every tp invocation catches the store up before the command runs: each active template materializes occurrences into the window now → now + 1 year. Idempotent — running twice creates nothing twice.

02Data model: one store, two new shapes

The store stays one JSON array in ~/.taskpilot.json. Plain v0.4 tasks pass through untouched; two extended shapes carry recurrence.

~/.taskpilot.json — Task[]
TemplateTaskthe generator — never listed as an actionable row
rruleRFC 5545 string, e.g. FREQ=WEEKLY;BYDAY=TU (D1)
dtstartISO anchor, local wall-clock (D8)
pausedboolean — pause stops generation, resume never backfills (D6)
lastGeneratedhigh-water mark that makes generation idempotent
OccurrenceTaska real task, materialized per scheduled date (D4)
templateIdthe series it belongs to — orphans must never exist
dueISO date-time — the field the future notifications feature consumes
skippedboolean — mutually exclusive with done (D5)

03Occurrence lifecycle

Per-occurrence states are independent of the series; only pause acts on the template.

pending
materialized, due date in view, listed by tp list
done
tp done — series unaffected, next occurrence still comes
skipped
tp skip — "chose not to", kept for history (≠ done, ≠ delete)
(template) paused
tp pause — no new occurrences; resume starts fresh, no guilt backlog

04Decisions

D1–D3 arrived with the user (briefless entry); D4–D9 were draft proposals settled in review round 1. Full rationale in the markdown's decisions table.

#decisioncall
D1Schedule storage● RRULE strings + dtstart on the task — user
D2Generation model● lazy, on-run; no background jobs — user
D3Lookahead● capped at 1 year — user
D4Occurrence representation● materialized first-class tasks, not virtual rows
D5Skip semantics● per-occurrence state, distinct from done/delete
D6Pause semantics● stops generation; resume does not backfill
D7Template edits● future occurrences only; history stays true
D8Time semantics● local wall-clock; DST shifts the instant, not the shown time
D9Long-absence catch-up● overdue occurrences collapse to the most recent

05Things to poke at

The round-1 agenda, kept with resolutions for the record — all items landed; the PRD is settled. The undecided hows (RRULE library, store migration mechanics, CLI surface syntax) are deliberately left for the technical design.

Virtual occurrences (computed at list time) instead of materialized rows?
Resolved in round 1 → materialized (D4): done/skip need a row to live on, and every existing command keeps working on plain tasks.
What does a user see after a month away — 30 overdue dailies?
Resolved in round 1 → collapse to most recent (D9). The alternative made the first run after a holiday unusable.
Do reminders belong in this feature?
Resolved in round 1 → no; deferred to a notifications feature PRD. This PRD only guarantees due exists to consume.
